# 项目永久记忆

## 版本

PGF v2.0

## 核心原则记录

### 为什么不用create_all

**原因**：`create_all`会创建所有表，但无法控制表的顺序和依赖关系。项目使用迁移脚本（Migration）来精确控制数据库结构变更。

**影响**：确保数据库变更可追溯、可回滚、可验证。

### 为什么先正式迁移

**原因**：正式迁移是将演练库数据迁移到生产环境的关键步骤。只有完成正式迁移，才能确保生产环境数据的完整性和一致性。

**影响**：避免数据丢失和不一致。

### 为什么自动情报后开发

**原因**：自动情报需要依赖稳定的数据结构和完善的主体档案。在主体治理完善之前开发自动情报，会导致情报质量低下。

**影响**：确保情报质量和准确性。

### 为什么UI最后统一

**原因**：UI统一是优化阶段，需要在核心业务功能稳定后进行。过早统一UI会浪费开发资源在频繁变动的界面上。

**影响**：提高开发效率，确保UI与业务功能匹配。

### 为什么主体治理优先

**原因**：主体（机构、人物）是系统的核心数据。主体数据质量直接影响关系网络、资源匹配、合作机会等所有业务功能。

**影响**：确保核心数据质量，为后续功能打下基础。

### 为什么数据库不能直接修改

**原因**：直接修改数据库会导致数据不一致、结构混乱、无法追溯。所有数据库变更必须通过迁移脚本执行。

**影响**：确保数据安全和可维护性。

## 经验教训

### 环境混用问题

**问题**：验收时使用不同端口和数据库，导致验收结果不准确。

**教训**：验收全过程必须使用唯一环境，通过日志确认端口和数据库路径。

### 认证绕过问题

**问题**：权限测试在认证禁用状态下执行，导致权限漏洞结论不准确。

**教训**：权限测试必须在认证启用状态下执行。

### 路由猜测问题

**问题**：根据模块名称猜测URL进行测试，导致错误报告。

**教训**：只测试真实注册的路由，先导出路由表再测试。

### 数据库路径错误

**问题**：启动脚本配置的数据库路径与预期不符。

**教训**：启动后通过日志和/health端点确认数据库路径。

## 决策原则

### 最小变更原则

任何修改必须是最小可验证变更，避免全仓重构。

### 向后兼容原则

新功能必须向后兼容，不破坏现有功能。

### 数据安全原则

不删除、不重建、不清空正式数据库。

### 权限最小化原则

用户只获得完成任务所需的最小权限。
