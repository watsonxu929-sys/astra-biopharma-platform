# T2 情报加工链路审计报告

审计时间: 2026-07-14
审计范围: P2.2之后的情报加工链路

## 一、审计发现

### 1. 767条候选由哪些规则生成

当前候选生成主要来自 `entity_extraction_service.py`:

- **organization**: 通过组织名称后缀模式匹配，每个区块中所有匹配都会生成候选
- **person**: 通过人名+职位模式匹配，同时生成person和field两种候选
- **project**: 通过项目/产品/药物名称模式匹配
- **event**: 通过关键词匹配，每个事件类型(融资/获批/合作/临床/招聘)独立生成候选
- **need/resource/risk/opportunity**: 通过关键词匹配生成

问题根源:
- 单篇文章可分割成多个区块(最多80个)，每个区块独立提取
- 事件提取中，命中多个关键词类型会分别生成候选
- 人物提取会同时生成person和field两种类型
- 没有单篇总候选数量限制

### 2. 每篇文章当前平均生成多少候选

当前逻辑下:
- 文章分割为多个区块(平均5-10个)
- 每个区块提取: 2-5个组织 + 0-3个人物(每人2条) + 1-3个事件 + 0-2个其他
- 单篇理论上限: 80区块 × (5组织 + 6人物 + 5事件 + 3其他) = 1520条

### 3. 哪些候选属于重复

- 同一组织/人物在不同区块中重复出现
- 同一事件类型在不同区块中重复匹配
- 人物提取同时生成person和field两种候选

### 4. 哪些候选只是关键词命中

- 所有事件候选仅通过关键词匹配，无上下文验证
- need/resource/risk/opportunity完全依赖关键词
- 没有证据位置验证

### 5. 当前摘要由什么逻辑生成

- RuleProvider: 直接截取前300字符作为摘要
- 没有专门的摘要生成逻辑
- 没有结构化模板

### 6. 当前是否真实调用AI

- 当前默认使用RuleProvider(规则模式)
- OpenAIProvider需要配置API Key
- 无有效Key时自动降级到RuleProvider

### 7. 无AI Key时系统使用什么逻辑

- 使用RuleProvider的确定性规则
- 事件类型通过关键词匹配
- 实体通过正则匹配
- 摘要截取前300字符

### 8. 哪些页面会向普通用户展示低质量候选

- `/processing/candidates/` - 候选列表页
- `/processing/review-queue` - 审核队列
- `/intelligence/legacy` - 原始情报列表

### 9. 哪些字段可以直接复用

- `v05f_collection_items` - 原始内容
- `v04g_source_snapshots` - 快照
- `v05g_extraction_candidates` - 候选
- `v05g_processing_jobs` - 加工任务

### 10. 本任务需要修改的最小范围

1. **entity_extraction_service.py**: 添加单篇候选数量限制
2. **processing_job_service.py**: 添加质量过滤和数量控制
3. **规则引擎**: 添加事件类型收敛和关键事实过滤
4. **模板**: 添加今日情报页面和质量诊断页面

## 二、问题清单

| 问题 | 影响 | 优先级 |
|------|------|--------|
| 单篇候选数量无限制 | 11篇生成767条候选 | 高 |
| 事件类型过多且重复 | 同一事件生成多条候选 | 高 |
| 人物同时生成person和field | 候选膨胀 | 中 |
| 摘要无结构化 | 用户无法快速理解 | 高 |
| 无内容质量门槛 | 低质量内容进入加工 | 高 |
| 候选无业务价值过滤 | 关键词命中即生成候选 | 高 |

## 三、修复策略

1. **质量过滤**: 在加工前检查内容质量
2. **数量限制**: 单篇最多5条关键事实+5个主体
3. **事件收敛**: 单篇只保留一个主要事件类型
4. **摘要规范**: 生成80-160字结构化摘要
5. **证据约束**: 所有候选必须有证据支持
6. **主体去重**: 同一主体在单篇中只保留一个
